# V9 workstream rules (shared by every coding agent)

1. Read first: docs/REPORT.md §55–61 (the V9 audit and plan — your scope is the section named in your brief), docs/STATE_MAP.md, docs/FRONTEND_CONVENTIONS.md, docs/SERVICE_BLUEPRINT.md, and the code you will change. §55 lists verified problems; re-verify anything before changing it.
2. Machine: ~5 GB RAM WSL, shared with the running dev stack (`npm run dev`: API :8000 with --reload, web :3100–3103 with HMR) and other agents. NEVER stop, restart or kill the dev stack or any process found with `pgrep -f`/`pkill -f` (the pattern matches your own shell). Wrap every heavy command in the build lock:
   `flock /tmp/claude-0/hg-build.lock <cmd>` — for typecheck, vitest, vite build, pytest (full or file), playwright.
   Run only the tests for your area while iterating (e.g. `cd server && flock /tmp/claude-0/hg-build.lock .venv/bin/pytest -q tests/test_v9_agency.py`).
3. Database: dev DB `hangyul_univ` (user hangyul / hangyul_dev). Alembic: create AND apply revisions inside `flock /tmp/claude-0/hg-migrate.lock`; first run `.venv/bin/alembic heads`, set `down_revision` to the current head (other agents add revisions too — there must always be ONE head), then `alembic upgrade head`. Hand-write revisions; name the file `v9_<area>_<short>.py`. Never drop/reset the dev DB. Seed additions go in `server/app/seed/extra_9x_<area>.py` (see extras.py) and must also be applied to the live dev DB with an idempotent script `server/scripts/v9_<area>_data.py`.
4. Not a git repo. Don't delete files you didn't create unless the brief says so; keep public API signatures working (additive changes; deprecate rather than remove).
5. i18n: every new UI string gets en + ko keys together, under a `v9` subtree of your namespace (agency.json / university.json / student.json / marketing.json, or a V5 namespace you own). Korean brand = 한귤. No hard-coded English in components. Other locales are handled by the localization workstream — do NOT edit other locale files.
6. Honesty: never fake an integration, partner, provider, inventory, delivery or rate. Unknown is shown as unknown. Metrics carry numerator/denominator/cohort; n < 5 withheld. No AI scores, no admission probability, no "guaranteed".
7. Every changed page: write its PRIMARY QUESTION as a comment at the top of the page component. Remove noise (cards, badges, tabs, zero-count chips) that doesn't help that question.
8. Tables: no core table may scroll sideways at 390/430/768/820/1024 — use DataTable column priority (`meta.priority`), row expansion or list rows on phones.
9. Tests: new pytest file `server/tests/test_v9_<area>.py` (tenant isolation for any new endpoint: other tenant → 404; student cannot reach staff endpoints), vitest for pure logic. Keep existing tests green for your area; if an existing test asserts old wording you changed on purpose, update it and say so in your log.
10. Screenshots: verify your screens by eye with `node scripts/qa/_demoshot.mjs <port> <email> <outdir> <widths> <path>` (Demo access sign-in; outdir under docs/qa/v9/<area>/) at 390 and 1024/1440. Look at them.
11. Log: write `docs/qa/v9/logs/<area>.md` as you go: each change → why (which §55 problem / §58–61 item) → files/API → test. Record what you did NOT do and why. Do not edit docs/REPORT.md (the coordinator does).
12. Finish with a ≤ 40-line summary: done items, API changes, migrations (revision ids), tests added + results, screenshots path, known gaps.
